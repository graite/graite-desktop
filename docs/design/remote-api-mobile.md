# Remote access, API and MCP, mobile

Three later features that share one seam: the daemon is an authenticated HTTP API and the
desktop UI is only its first client. This doc designs them far enough that v1 builds in the
cheap hooks and nothing needs a rewrite later.

## 1. API and MCP

### Surface
- Everything the UI uses is exposed under a versioned prefix `/api/v1/…` from M0, with
  OpenAPI generated by FastAPI (also the source of `packages/api-types`). The prefix is the
  stability promise; internal experiments live under `/internal/`.
- Resources: pages (tree, get, put with `base_hash`, create, move, trash), search,
  proposals (list, accept, reject, edit-accept, revert), jobs, cron, models, media, events.

### Tokens and scopes
One `tokens` table (M2) with `id, name, kind (ui|api|device), scopes, hash, created_at,
last_used_at, revoked_at`. Tokens are shown once at creation and stored hashed.

| Scope | Allows |
|---|---|
| `read` | read pages, search, list proposals and jobs |
| `propose` | create proposals (the agent-class write) |
| `write` | direct writes through fileops as a human-class actor (the owner's own scripts) |
| `apply` | accept, reject, revert proposals |
| `admin` | tokens, models, settings, cron |

**Direct write vs propose is a token scope, not a route.** `PUT /api/v1/pages/{path}` with
a `write` token goes straight through fileops; with only `propose` the same call creates a
proposal. Activities record `actor = api:<token-name>`, so the audit log distinguishes a
script from the UI and from agents (`agent:<job-id>`).

### Chat through the API — two doors
1. `POST /api/v1/chat` — the SSE contract the UI uses: page context, instructions cascade,
   tools, proposals, `page_updated` events. Use this to drive the vault agent from scripts.
2. `POST /v1/chat/completions` — an **OpenAI-compatible shim**. The `model` field selects
   the mode:
   - a catalog id (`qwen3-8b-q4`) → raw passthrough to that llama-server;
   - `graite/agent` → the agent loop with the vault root cascade and the full tool set;
   - `graite/<page-path>` → the agent loop scoped to that page (its cascade, its skills).
   Streaming works as in OpenAI. Tool calls the agent makes are internal; proposals appear
   in the review queue as usual. This turns every OpenAI-speaking client — phone chat apps,
   Open WebUI, editor plugins, Raycast — into a Graite client with no mobile work.

### Running things automatically
- `POST /api/v1/jobs` with `kind: agent_run`, `instructions`, `page_path` — the same job the
  cron scheduler creates. `POST /api/v1/cron` to schedule it.
- **Webhooks** (M8): `POST` to configured URLs on `proposal`, `proposal_decided`,
  `job_update`, signed with a per-webhook secret. Enough for n8n/Zapier-style automation.

### MCP server
Built on the official `mcp` SDK's low-level server, mounted in the daemon
(`graite/mcp/server.py`). **The local slice has landed (D30, D31); the rest is M8.**
- **Tools** = the registry's read/search/propose set, with the schemas the agents already
  use. Write-free by construction, so Claude Code, Claude Desktop or Cursor can work on the
  vault only through proposals, and a page's auto-apply setting applies to them as it does
  to an agent. `schedule` is left out: it would start a local run that can read local-only
  pages.
- **The client is treated as a cloud model.** Pages under `cloud: local-only` cannot be read,
  searched or proposed against. Proposals are attributed (`conversation_id = mcp:<client>`)
  and the review card says "via MCP".
- **Prompts** = skills (`SKILL.md` bodies).
- **Resources** = pages as `graite://<vault-id>/<path>` (markdown body + frontmatter): M8.
- Transports: **stdio** through `graite-daemon mcp`, a bridge that finds the running daemon
  in `~/.graite/daemon.json` and so survives the per-launch port and token; **streamable
  HTTP** (stateless JSON) at `POST /mcp` behind the same bearer token. Settings → Connect AI
  apps shows what to paste.
- Not yet: remote clients (claude.ai and ChatGPT connectors call from the cloud and need a
  public HTTPS URL plus OAuth; that is the M9 remote-access work), scoped tokens (D16).

### MCP client
External MCP servers' tools registered as skills (the Rowboat pattern). They have side
effects outside the vault (send an email, create a ticket), so they get a new proposal
kind, **`action`**: the tool call is queued with its arguments and only executed on
accept. Same review UI, same audit trail. Later than the server (M8+).

## 2. Remote access: local models on your phone

"Run local models on your phone" means a thin client on the phone and inference at home.

### Requirements, in order
1. **Headless daemon.** `graite-daemon --serve --vault <path>` runs without the Tauri window
   (systemd, launchd, or the desktop app minimized to the tray). The daemon must never
   import Tauri; that is a hard rule from M0.
2. **Remote-access toggle**, default off, in Settings → Remote. Turning it on binds an
   additional listener chosen from the transport below, and refuses to serve plain HTTP on
   a non-loopback, non-WireGuard interface.
3. **Transport, three tiers.**
   - **Tailscale (recommended, first).** WireGuard mesh, nothing public, MagicDNS, and
     `tailscale serve` provides HTTPS with real certificates. Graite only needs to bind to
     the tailnet address and ship a docs page. The phone installs Tailscale.
   - **Cloudflare Tunnel or Pangolin** for a public URL, with Cloudflare Access or the
     daemon's own tokens in front. For sharing with people outside the tailnet.
   - **Graite relay** (optional, self-hosted). Devices connect outbound over WebSocket; a
     phone hits `https://relay.<domain>/<device-id>`. The relay is a pure pipe and stores
     nothing. The most product-like option and the most work; it is the piece that would
     be self-hosted in the cloud.
4. **Security off loopback.** Per-device tokens (`kind = device`) with scopes and
   revocation; rate limiting and lockout on auth failures; strict CORS; activities record
   `actor = device:<name>`; a "remote actions" filter in the Activity view.
5. **Pairing.** Settings → Remote shows a QR code encoding `{url, device_token, scopes}`.
   The phone client scans it.

### The no-app phone client: PWA at `/m`
The daemon serves the same React app with a mobile layout at `/m`: chat (with the page
picker), search, the review queue (accept and reject on the go), reading pages, and voice
memo recording that uploads to the transcribe job. Installable on iOS and Android. Together
with the OpenAI-compatible endpoint this covers "use my models from my phone" without a
native app.

### Practicalities
The home machine must be awake (document power settings; Wake-on-LAN later). `model_status`
events tell the phone when a model is loading. SSE streams fine through all three transports.

## 3. Mobile app and sync

Three readings of "sync", in increasing cost:

- **A. Thin client, no offline.** The PWA over the tunnel. Covered by §2.
- **B. Third-party file sync.** Syncthing, iCloud, Dropbox or git syncs the vault folder;
  a mobile client opens the local copy. Graite already tolerates external changes
  (watcher, hashes, `sync_safe`). `.graite/` must be excluded from sync since it is
  per-device state. Conflicts are the sync tool's problem, and the mobile app would need
  its own editor and converter with no daemon.
- **C. Graite sync, daemon as hub (recommended end state).** The desktop daemon is the
  source of truth; the phone keeps a partial replica and works offline.

### C in detail
- **Change log.** A monotonic `change_seq` on every page and attachment in the index (added
  in M1). Deletions leave tombstones.
- **Endpoints.** `GET /api/v1/sync/changes?since=<seq>` returns paths, hashes, frontmatter
  and tombstones; `GET /api/v1/sync/files/{path}` fetches content; `PUT /api/v1/sync/files/{path}`
  with `base_hash` applies the same optimistic-concurrency rule the editor uses.
- **Attachments** are fetched lazily by content hash (hashed in the index from M5), with
  per-folder selective sync.
- **Conflicts.** 3-way merge on markdown with the same `node-diff3` the editor uses. When
  the merge is not clean, the phone's version becomes a **proposal** in the review queue
  with the desktop version as base. Conflicts get the UI that already exists instead of
  `.conflict.md` litter.
- **App shell.** Capacitor (or Tauri Mobile once stable) wrapping the same React app. A
  `platform` adapter (M0) swaps the daemon for a local SQLite + file store; `md-convert`
  runs on-device. No local models in the first mobile version; inference goes over the
  tunnel when online.
- **Encryption.** A relay stays a pure pipe, so no end-to-end work is needed. If cloud
  storage for sync is ever offered, encrypt client-side.

### Sizing (solo, rough)
API and MCP about 2 weeks; headless, remote and PWA about 3 weeks; sync plus a mobile app
8–10 weeks. Sync is a v2-scale project; A and B ship first.

## 4. Hooks built into v1

| Hook | Milestone | Why |
|---|---|---|
| Daemon has zero Tauri dependency; `--serve` headless flag | M0 | Tunnel and relay |
| `/api/v1/` prefix and OpenAPI from day one | M0 | Stability for API and MCP clients |
| `platform` adapter in the React app (desktop via Tauri, web via fetch, mobile via Capacitor); `vault://` URLs produced only by the adapter (web uses `/media/<path>`) | M0 | PWA and mobile reuse the UI unchanged |
| `activities.actor` carries a client identity: `ui`, `api:<name>`, `device:<name>`, `agent:<job-id>` | M1 | Audit for remote and automated actors |
| `change_seq` on pages and attachments, tombstones on delete | M1 | Incremental sync |
| `tokens` table with `kind` and `scopes`, hashed at rest | M2 | API and device tokens share it |
| Attachment content hashes in the index | M5 | Lazy sync by hash |
