| D17 | 2026-09-14 | **Graite owns the llama.cpp build matrix** (`graite-llama` repo: pinned upstream tag, CI builds, smoke tests, signed manifest) | Upstream prebuilt zips; build on the user's machine; llama-cpp-python wheels | Upstream prebuilts lack Linux CUDA and Linux arm64 CUDA and rename assets; owning the matrix gives a stable update channel and a tested binary per platform. | D23 | 2026-09-16 | **Agents and workflows are Markdown files** in `_agents/` and `_workflows/` folders (vault root or any page folder), like `_skills/`: frontmatter holds scope, mode, model, tools and an optional cron `schedule`, the body holds the instructions; a workflow lists ordered steps, each an agent plus optional extra instructions and scope, and every step sees the previous step's answer as a source. | D22 | 2026-09-16 | **The review queue ships as designed in ARCHITECTURE §8, with two adjustments**: the one-time auto-apply opt-in is stored per setting source in the vault index (`meta.auto_apply_opt_in`), not in `config.toml` (no TOML writer, and losing `.graite/` only means being asked again); and user-initiated UI actions ("Turn into page", editor saves, moves) stay direct writes, only model-initiated changes become proposals. | D25 | 2026-09-17 | **One "Model server" connection kind for every OpenAI-compatible endpoint**, OpenRouter included; Claude stays its own kind because its API differs. | D24 | 2026-09-17 | **Unattended runs get their own prompt** (`answer.agent_messages`): the agent's cleaned instructions are the system prompt's task, the user turn is only the trigger ("Run now.", "Scheduled run at …", "Page [[X]] was updated"), CLARIFY is forbidden and a leftover question ends the run as `needs_input`. Every tool call is a `run_steps` row (`kind: tool`, arguments in, page/proposal/summary out), the report is stored in `output_json.answer`, tokens are summed per run, and each change publishes a `run_update` event. Saving an agent rejects unknown tool names, propose tools in Ask mode, and trigger paths outside its scope. | Reuse the chat prompt with the instructions as the question | A chat prompt tells the model to answer and cite; an agent must act, and its run must say what it did without opening a debugger. |
| D23b | 2026-09-17 | **Applying a proposal is not the editor's own write**: the review client sends no request id, so the `file_changed` echo reloads the open page instead of being ignored. "Rebased" is judged on a body hash (`base_body_hash`), not the file hash that frontmatter touches on every save. Root-level `propose_create` passes an empty parent. Optional tool arguments are nullable and not required. Conflicts while applying return 409 or a tool error, never a 500 or a failed turn. `opt_in_source` travels with the proposal. | Ignore all echoes; keep guessing the setting's folder in the UI | The editor must show what the user just accepted, and an accepted proposal must never poison the next save with a false conflict. |
| D26 | 2026-09-17 | **The vault is chosen in the shell, not baked into the launch**: `vaults.json` in the Tauri app-config dir remembers the current and recent vault folders; `GRAITE_VAULT` still wins for launchers. With no remembered vault the daemon is not spawned and the webview shows a picker; switching stops the daemon and starts one on the new folder (two daemons must never share one `.graite/index.sqlite`). The workspace remounts per vault and per-vault browser storage is keyed by a hash of the path. `GET /health` says whether a folder is new (`is_new`, `pages`). Under `just dev` the daemon owns the vault and switching is disabled. | Hot-swap vault state inside the daemon; a marker file in the vault | Every piece of daemon state is per vault and torn down in one place; a restart is a second of latency for a switch that happens a few times a year, and rule 6 forbids a marker. |
| D27 | 2026-09-18 | **Proposals show in the page where they apply, as editor decorations, placed client-side**: `packages/md-convert` reports each top-level block's source span (`toBlocksWithSpans`); the desktop finds an edit's `old_text` in the body on disk (one occurrence, like the daemon) and anchors a suggestion card under the blocks it touches. | D28 | 2026-09-18 | **Schedules are built in words; cron is the advanced path**: `lib/schedule.ts` maps every few minutes / hourly / daily / weekdays / weekly (day pills) / monthly (1–28 or last day) to five-field cron and back, and describes any expression it knows; everything else stays a custom expression. The Schedules view can create a schedule (an agent, or ad-hoc instructions) and edit the name and timing of ones made there or in chat. | Local-time schedules (a timezone per schedule or per vault); a cron library on the client; a preview endpoint for next runs | UTC stays the single clock across frontmatter, live notes, the `schedule` tool and headless servers; the hint covers the everyday confusion. The recognised shapes are few enough to own in ~150 lines, and saved rows already show the daemon's `next_run_at`. |
| D29 | 2026-09-18 | **A page's attachments can be listed, trashed and purged; "in use" is a filename search**: `FileOps.list_attachments` reads `<page>/_assets`; a file counts as used when its stored name (unique `<uuid>-` prefix) occurs anywhere in the raw `page.md` of the owning page or a descendant, which covers `graite:media`/`graite:text` fences, media properties and `../_assets/` links from transcript subpages. `trash_attachment` moves the file to `.graite/trash/<ms>-<name>/` with an `.origin.json` of `kind: attachment` and the owner's stable page id; restore finds the page by that id (so renames and moves are fine) and never overwrites. Trashing a used file needs `force` (409 otherwise). `DELETE /api/v1/trash[/{id}]` empties the trash for good. `TrashEntry` gained `kind`, `file`, `page_id`, `size` and `/media/location` gained `path` (additive). | Deleting the file when its block is removed; indexing asset references in SQLite; a vault-wide attachments screen; permanent delete straight from the page | Removing a block is undoable and a file may be used twice (a transcript subpage links its source), so deletion has to be a deliberate act. The uuid prefix makes a substring match exact without a new table the watcher would have to keep current. Trash keeps one recovery path for pages and files. No page file is rewritten (rule 5). Emptying the trash ends the ability to revert an accepted delete proposal; the confirmation says so. |
| D30 | 2026-09-18 | **MCP server = the Act-mode registry, for local clients, treated as a cloud model** (`graite/mcp/server.py`, `POST /mcp`): the official `mcp` SDK's low-level `Server` lists `skills/tools.py` `TOOLS` with their existing JSON Schemas and dispatches through `Registry.invoke`; a fresh registry per call (`load_skill` narrows it). | D31 | 2026-09-18 | **MCP clients launch `graite-daemon mcp`, a stdio bridge, and find the daemon through `~/.graite/daemon.json`**: the daemon writes `{url, token, pid, vault, version}` there (mode 0600, atomic) once it is bound and removes it in the lifespan teardown (pid-guarded; uvicorn re-raises SIGTERM after the lifespan, so cleanup after `server.run()` never runs). | D32 | 2026-09-18 | **Extracted text never enters the vault as its own file**: an "add here" transcript or OCR result is carried by the job (`Extraction.text`, persisted with the job row in `.graite`) and inserted into the page by the editor; `_assets` holds only what the user attached. `AttachmentInfo.generated` marks the `<uuid>-transcript.md` / `<uuid>-ocr.md` files earlier versions left behind: the attachments list hides them, keeps any that an old `graite:text` block still shows, and moves the unused rest to the trash in one step. `Extraction.file` stays for jobs finished before the change. | Keep writing the files and only hide them; delete leftovers automatically; store results under `.graite/media/` | The file was read exactly once, by the editor, and then duplicated text that already lives in `page.md`: clutter in the list, and the orphan-file problem D29 set out to fix. | D33 | 2026-09-18 | **CPU-only `onnxruntime` is a sanctioned runtime for exactly two small voice models**: Silero VAD (2 MB) and pipecat Smart Turn v3.2 (8 MB int8), in `graite/voice/vad.py` and `voice/turn.py`, imported lazily. | D34 | 2026-09-18 | **The assistant's voice is Chatterbox Multilingual on GGML, run by an external `crispasr --server` the user points Graite at** (`voice/engines/crispasr.py`, config `tts_binary_path`, catalog role `tts` with the two `cstr/chatterbox-GGUF` v3 files), behind a small `TTSEngine` protocol (`voice/tts.py`) instead of the chat `Provider` that VISION/PLAN sketched. ONNX on CPU was estimated at 1 to 2 times real time, too slow for conversation; the NVIGI plugin is Windows DLLs. A voice engine has no messages or tools and streams PCM, so forcing it into `Provider` would help nobody. The port is young and single-maintainer: `get_engine()` is the only place that knows engines, and the stub engine keeps the whole path testable. |
| D35 | 2026-09-18 | **The personal assistant is an `_agents` definition with `assistant: true`** (one per vault; extra keys `memory: <page id>` and `voice: {...}`; body sections Personality, Context, Guidelines, Goals), **and its memory is ordinary pages** (`<Name>/Profile`, `Playbook`, `Journal`) whose root asks for `autonomy: auto-apply` and still needs the one-time opt-in. | D36 | 2026-09-18 | **The background loop is a job kind of its own, `assistant_loop`, with a fixed cron source `assistant:loop`; a debounced `assistant_reflect` job files memory after a conversation; both are `preemptible`** and a `ForegroundGate` (`assistant/presence.py`) cancels and re-queues them and pauses the `model` lane while the user talks to the assistant. | D37 | 2026-09-18 | **A second WebSocket, `/api/v1/voice/session`**: binary PCM16 16 kHz up, JSON events plus binary PCM16 24 kHz down, `?token=` auth like `/events`; **half-duplex by default** (microphone frames are dropped while the assistant thinks or speaks; interrupt by button or Space), voice interruption is an opt-in for headphones. | D38 | 2026-09-19 | **Interrupting by speaking is on by default, behind three gates** (`voice/bargein.py`, supersedes D37's half-duplex default): while the assistant has the floor, (1) the VAD must hear ~0.2 s of speech, (2) louder than the echo we expect — the daemon knows the PCM it sent and the client's playback position, pinned to the microphone's own frame clock, and learns the speaker-to-microphone gain against a peak-held reference (no delay estimate) — and (3) a ducked ~1 s snippet goes to the resident Whisper, and `judge()` lets only real words through: not silence, not low-confidence words imagined into noise, not an ordered stretch of what the assistant is saying, not "mm-hm"; two words or a stop word interrupt. Measured with the real engines and a simulated room (assistant audio fed back 150 ms late at -9 dB): no candidate on echo alone, noise bursts either ignored or rejected (one hallucinated sentence caught by Whisper's log-probability), a spoken interruption confirmed every time about 1 s after sustained speech began, with playback ducked after ~0.4 s. Estimating the echo delay was tried first and dropped: envelope correlation called a user who starts talking "echo". A WASM canceller needs `wasm-unsafe-eval` in the CSP and would still leave residue the word check has to catch. Fails safe: speakers louder than the user keep the gate shut, and the button and Space always interrupt. |

| D42 | 2026-09-21 | **The assistant's own pages are written without review** (`assistant/memory.py`): `memory.ensure` records the auto-apply opt-in for the memory root alongside the frontmatter it already wrote, and `memory.info` re-confirms it whenever the root itself is the setting's source.
